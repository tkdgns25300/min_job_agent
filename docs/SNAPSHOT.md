### 주제 1 — 우리가 넣는 필드 (`jobs`)

#### 결정: **교회 행을 만들지 않는다. `church_id`는 NULL로 둔다.**

이유는 "100% 정확해야 한다"(운영자)를 만족시킬 방법이 **병합을 아예 안 하는 것**뿐이기 때문이다.
교회 묶기를 실측해 봤더니 자동 95%까지는 되지만 **사각지대가 남는다**:

```
(교회명 + 광역) 으로 묶기 → 1,203개 그룹
  공고 1건뿐             632개
  여러 건 · 신호 일관     511개   ← 전화·이메일·도메인이 일치
  여러 건 · 신호 엇갈림    51개
  여러 건 · 신호 없음       9개
  ⚠ 일부 공고에 연락처가 없어 **충돌을 확인할 수 없는** 묶음  58개
  ⚠ 전 공고에 연락처가 없어 **아무 검증도 못 하는** 묶음      9개
     → 이 67개는 '일관'으로 보이지만 실제로 다른 교회일 수 있다
```

두 오류의 무게가 다르다: **다른 교회를 합치면**(B교회 페이지에 A교회 공고) 되돌리기 어렵고 이미
공개돼 있다. **같은 교회를 나누면** 중복 행이 생기지만 나중에 병합할 수 있다. 그래서 기본값을
"증거 없으면 합치지 않는다"로 뒤집었고, 끝까지 밀어 **아예 만들지 않는** 쪽으로 갔다.

⚠️ 강한 식별자(연락처)로만 묶어도 100%가 아니다 — 같은 연락처에 다른 교회명이 **83건**
(`대구대동교회`/`대동교회` 같은 표기 차이도, 교단 사무실 공유도 섞여 있다).

#### 그래서 이 모양이 된다

```
crawled job
  church_id     NULL              모른다 (정직)
  church_name   "점촌제일교회"      공고가 말한 그대로 · NOT NULL
  region        GYEONGBUK         enum 18키
  dedup_key     묶음 id            끌어올림을 하나로 만든 결과
        │
        ▼  교회가 min_job 가입 → 인증
   "이 공고들이 귀 교회 것입니까?"   ← 이름+지역이 맞는 후보만
        ▼  교회가 확인
  church_id 채워짐 → 교회 상세 페이지 활성 · 재공고 이력 작동
```

**우리는 교회를 만들지도, 묶지도, 이름을 비교하지도 않는다.** 비교는 claim 시점에 그 교회가 한다
(사람이 보면 `대구대동교회`와 `대동교회`가 자기 교회인지 안다).

#### 우리가 채우는 필드 · 실측 커버율

| 그룹 | 필드 | 커버율 |
|---|---|---|
| 교회 | `church_name`(NOT NULL) · `region`(enum) · `church_id`=NULL | 96% / 80% |
| 분류 | `job_kind` · `position` 또는 `role` · `department` | AI |
| 조건 | `employment_type`(51%) · `qualification`(90%) · `headcount`(65%) · `start_timing`(45%) | |
| 처우 | `pay_min/max/note/period`(75%) · `housing_provided/note`(40%) · `benefit_note` | |
| 지원 | `contact_email`·`contact_tel`·`contact_link`·`contact_post` | 89% |
| | `required_docs`(88%) · `optional_docs` · `process_steps`(42%) · `work_days` | |
| 본문 | `title` · `description`(요약) · `source_url` · `posted_at` · `deadline`(75%) | |
| 메타 | `dedup_key` · `confidence` · `heresy_flag` | 우리 계산 |

min_job이 채우는 것: `source=OPERATOR` · `owner_id=NULL` · `status` · `featured_tier` · `created_at`

비어도 되는 것: `denomination`(명시 2.8%) · `deadline` · `pay_*` · `housing_*` ·
`employment_type` — ⚠️ **DEFAULT로 값을 지어내지 않는다**("언급 없음"을 "미제공"으로 바꾸면
우리가 틀린 정보를 생산한다).

#### `region`이 `jobs`·`churches` 양쪽에 있는 이유 (정규화 위반 아님)

```
churches.region   교회가 어디 있나       (교회 소재지)
jobs.region       이 자리가 어디서 일하나 (근무 지역 · 필터 대상)
```

대개 같지만 다를 수 있다(`온누리교회 회복사역본부` · `연세대 원주의과대학 교목실 협력 교역자`).
같은 사실을 두 번 저장하는 게 아니라 **우연히 대개 일치하는 두 사실**이다. 그리고 크롤 공고는
`church_id`가 없으므로 **`jobs.region`이 유일한 저장 위치**다. 해외 공고가 실제로 23건 있어
`OVERSEAS` 키가 필요하다(이스탄불·뉴질랜드 타우랑가·호주 퍼스 등).

#### ② 중복 · 끌어올림 — **확정**(2026-08-06 최종 · 정본은 SPEC §4.1)

```
dedup_key = 정규화교회명 : region : position : department : 라운드번호
            라운드: 직전 공고와 간격 ≤ 3개월이면 같은 라운드, 넘으면 새 라운드(재공고)
            같으면  →  대표 1건 · posted_at 최신
            다르면  →  별개 (재공고로 보존)

⚠️ 구조화 **뒤에** 계산한다(position·department 가 구조화 산출물이다)
⚠️ 네 요소 중 하나라도 없으면 병합하지 않는다 (지역 없는 공고 18.6% → 각각 단독)
⚠️ 제목·마감일은 키에 넣지 않는다 (아래 근거)
```

**제목 정규화**: 대괄호·괄호 안 제거 · `끌어올림`·`재공고`·`긴급`·`추가`·`수정` 제거 ·
공백·기호 제거. 실측에서 같은 자리인데 게시판마다 제목이 달랐다:
`점촌제일교회에서 전임 사역자를 청빙합니다` / `점촌제일교회에서 전임사역자 청빙 광고` /
`[끌어올림]전주아멘교회 전임 사역자`.

⚠️ **왜 처음 안(연락처 + 직분 + 부서)을 버렸나** — 두 가지 이유다:
1. **직분·부서는 AI가 뽑는 값**이라 구조화가 끝나야 알 수 있고, 틀릴 수 있다. 교회명+제목은
   **지금 있는 값**으로 계산된다(MVP에 맞다).
2. **연락처만으로는 다른 자리를 합친다** — 실측 322개 묶음(1,438건)이 연락처는 같은데 제목이
   다르다. 한 교회가 여러 자리를 동시에 뽑는다:
   `춘천새순교회` 연락처 1개 · 73건 · 제목 5종(`예배팀 파트교역자` / `예배팀 원데이 교역자` …)

| 교회명 + 연락처 | 1,629건 | 48.9% | 제목이 달라도 합침 → 다른 자리 위험 |

**중복을 안 합치면 안 되는 이유**: 42%가 같은 글의 반복이다. 그대로 올리면 min_job 목록 절반이
중복이고 재공고 카운트가 거짓이 된다(`점촌제일교회` 한 자리가 "31회 공고"로 보인다).

⚠️⚠️ **아직 논의가 남은 지점**
- **교회명을 못 뽑는 114건**(3.6%)은 어떻게 묶나 — 지금은 각각 별개로 남는다
- **제목이 크게 다른 같은 자리**는 못 잡는다(`전임 사역자를 청빙합니다` vs `전임사역자 청빙 광고`는
  정규화로 잡히지만, 완전히 새로 쓴 제목은 못 잡는다) → 구조화 후 직분·부서로 정밀화할 여지
- **마감일을 판정에 쓸지** — 실측 71%가 마감일을 갖고 있다. 마감일이 같으면 제목이 달라도 같은
  공고일 가능성이 높은데, 지금 잠정안은 마감일을 안 쓴다
- **3개월 창의 의미** — 우리 수집 범위가 정확히 3개월이라 사실상 "이번 수집분 안에서 같은 글이면
  하나"가 된다. 데일리 수집으로 넘어가면 창의 뜻이 달라진다(원장에 남은 과거 공고와 비교해야 함)
- **교차게시**(같은 공고가 여러 게시판에) — 교회명+제목이 같으면 자동으로 합쳐지지만, 게시판마다
  제목을 바꿔 올리면 안 합쳐진다

## 2026-08-05 (5차) — 첫 3개월 실전 수집에서 나온 것 전부

운영자가 `--months 3`을 돌려 10곳(1,480건)까지 진행한 뒤 Ctrl-C. 거기서 나온 문제 4개.

**① `Crawl-delay`를 남의 규칙에서 가져왔다 — SJS가 6.7배 느렸다**

```
SJS robots Crawl-delay 10.0s 적용      ← 우리에겐 해당 없는 값이었다
```

SJS `robots.txt`는 `Crawl-delay: 10`을 **bingbot·msnbot에만** 걸어 두고 `User-agent: *`에는
값이 없다. 우리 폴백이 "UA 그룹을 구분하지 않고 최댓값"을 쓰면서(그리고 *"간격은 늘리는 쪽이
안전하다"*고 docstring에 정당화까지 해 두고) 남의 값을 가져왔다.

그 논리가 왜 틀렸나 — 사이트는 **싫어하는 SEO 봇에 30~60초를 건다**(SJS도 SemrushBot·
AhrefsBot을 전면 차단해 뒀다). 그룹을 무시하면 그 한 줄이 우리 수집을 사실상 멈춘다.

→ 그룹 단위로 파싱하도록 고쳤다. 덤으로 표준 파서의 두 번째 결함도 드러났다: **그룹 밖에 떠
있는 지시자를 `*`에 붙인다**(`Crawl-delay: 99`가 어느 그룹에도 없는데 99를 돌려준다). 그래서
**지연 판정은 우리 파서가 정본**이고 표준 파서는 `Disallow`에만 쓴다.

**실측 결과: 30개 호스트 중 우리에게 `Crawl-delay`를 거는 곳은 0곳.** 전부 기본 1.5s다.

**② 내용 없이 올라온 글을 영구 실패로 두고 있었다**

`YTUS 25309`는 본문이 `<p>&nbsp;</p>`다 — 작성자가 내용 없이 올렸다. 어댑터가 이걸 실패로

1. `base.absolute_url()` — 합칠 수 없는 주소는 예외가 아니라 `None`. `attachments_in`·

   그것이다. ⚠️ **`Exception`으로 넓히지 않았다** — 그러면 어댑터 버그가 "실패 1건"으로 묻힌다

4. `crawl_run`이 **열린 채 남았다**(`finished_at: null`). 크래시·Ctrl-C가 실행 기록을 영구히

   감싸 기록만 남기고 예외는 올려보낸다(중단 사유는 `error_detail["_aborted"]`, 소스 실패
   수에는 세지 않는다).

**교훈** — 격리 층이 있어도 **어떤 예외를 잡는지가 격리의 실체**다. 30곳 병렬 수집에서 한 글의

**남아 있는 것** — 그 실행에서 DAESHIN 36건이 저장됐고 원장에 있다. 재시작하면 건너뛴다.

## 9. 크롤 파이프라인·데이터 설계 (2026-07-27 상세)

> 이 세션에서 확정한 파이프라인·배포·저장 설계. §6 `[x] 파이프라인·배포 방향`의 상세본. 정식화(SPEC/CLAUDE + `src/`) 시 이 설계를 기준으로 한다.

### 9.1 파이프라인 (①~⑥)
```
① 소스 레지스트리(repo config) ─┐
② 시크릿(GH Secrets) ───────────┤→ [GitHub Actions 크롤 실행]
③ 원장 조회(source_data) ───────┘   (이미 본 글번호 skip)
      ▼ fetch → raw 최대 추출 (이미지 공고는 vision으로 텍스트화)
④ source_data      (raw + 원장 · 불변)
      ▼ 구조화(Gemini 2.5 Flash) + 교단 확정(명시·명부=규칙 / 그 외 AI추정 ai_guess)
⑤ review_data      (PENDING)
      ▼ 운영자 검수(min_job admin) — 승인/수정
⑥ churches / jobs  (공개 · 요약 + source_url)
   ↳ crawl_run: 시작에 INSERT(run_id 확보) → 종료에 요약·에러 UPDATE · source_health UPSERT → 이상 시 경보
```
- ①~⑤ 자동 · ⑥ 사람 게이트. **dedup 2종**: 글번호(수집 시 skip) / 교차게시 병합(검수 시).

### 9.2 트리거·배포
- **배포 = GitHub Actions.** 크롤러 코드가 repo에 있고 `.github/workflows/crawl.yml`만 두면 GitHub이 매일 러너를 띄워 실행 후 삭제. **상시 서버 없음 · 무료 한도 내 $0.**
- **트리거**: 매일 cron **자동**(DAILY·파라미터 없음) + 수동 `workflow_dispatch`(DAILY 즉시 재실행). **백필은 로컬 수동**(mode=BACKFILL·최근 3개월 · SPEC §7).
- **증분**: 게시판별 `source_health.last_run_at` 이후 + **글번호(`external_id`) 원장 대조로 최종 판정**(날짜보다 정확). ⚠️ **초기 백필은 운영자가 크롤러로 수동 실행** → `source_data`에 원장이 채워져야 데일리가 중복을 안 만듦(엑셀로 jobs만 손입력 시 원장 비어 중복 발생).

### 9.3 저장 위치
- **GitHub(repo)**: 코드 + **소스 정의 config**(31곳 URL·셀렉터·flags·`enabled`). **공고 데이터는 없음.** 추가/제외 = config 커밋(`enabled:false`로 제외해도 이력 보존).
- **Supabase**: 실제 데이터 전부(raw→검수→공개 + 운영 상태). 무료 티어.
- **GH Secrets**: Supabase service key · Vertex 키(env — repo/DB에 노출 X).

### 9.4 Supabase 스키마 (크롤러 4테이블 + 목적지)

**① `source_data` — 원자료 + 원장 (불변, write-once)**

### 9.5 실패 감지
- **하드**(접근 제한·URL 변경·타임아웃): HTTP 비2xx/000 → GitHub Actions 빨간불 + 이메일(자동).

### 9.6 admin 크롤 대시보드
`crawl_run`(최근 실행: 언제·신규 N·실패 M·소요) + `source_health`(게시판별 마지막 성공·건수·연속실패) + `review_data` PENDING 카운트를 min_job admin이 읽어 표시. → "오늘 몇 건 추가/실패, 언제 긁었나" 가시화.

### 9.7 스키마 거버넌스 ★
- **크롤러 staging 스키마(`source_data`·`review_data`·`source_health`·`crawl_run`)는 `min_job_agent`가 소유·문서화·마이그레이션.** min_job 리포는 건드리지 않는다.
- **`../min_job/docs/DATA.md`는 최종 output(`churches`/`jobs`) 스키마만 정본.** 크롤러는 그 output 모양에 맞춰 승격만 하고, 그 위 staging 4테이블은 이 리포 소관.
- 물리적으로는 **min_job Supabase 프로젝트에 함께** 두되(같은 DB라 검수·승격이 단순), **정의·변경 관리는 이 리포**에서. (CONTRACT §3 "크롤러 전용 스테이징 필드"와 정합)

### ① fetch 층이 하는 일 (완료 · 재작업 금지)

모든 HTTP가 여기를 지난다(어댑터·파이프라인의 직접 `httpx` import는 ruff TID251로 금지).
담당: **UA 31곳 동일(브라우저) + 브라우저 헤더 세트** · **config 인코딩 우선**(EUC-KR→cp949) · 타임아웃 20s ·
재시도 3회(429·5xx·연결오류만 · 지수 백오프+지터) · 같은 소스 요청 간격 1.5s · 세션 쿠키(`needs_session`) ·
**본문 길이 하한 200자**(200 OK + 빈 본문을 성공으로 오판하지 않기).

**하지 않는 것**(의도적):
- `www_required`·`http_only` → 이미 `list_url`에 있고 레지스트리가 로드 시 강제. 상대 URL은 `urljoin`이 물려준다. **코드 넣지 말 것.**
- robots `Disallow` → `RESPECT_ROBOTS_DISALLOW=False`(운영자 판단 §2). `Crawl-delay`는 준수(`RESPECT_CRAWL_DELAY=True`).
- `spoof_ua` → UA가 31곳 동일해져 **코드 분기가 없다**(실측 기록으로만 잔존 · §2).
- `soft_200`·`image_only` → 전송이 아니라 **본문 판정**이라 어댑터·파이프라인 몫.

상세   /board/view/trXXR/{id}                       id = 경로 끝 숫자

목록  tr 21개 = 헤더 1 + 공지 2(tr.notice-row) + 공고 18

⚠️ **2페이지 이후 상세 링크에 `/page/N`이 붙는다**(실측 2026-08-04): `/board/view/trXXR/25556/page/2`.
URL 마지막 조각을 id로 쓰면 **한 페이지 20행이 전부 `"2"`** 가 된다(중복 가드가 실제로 잡았다).

⚠️ **fixture 마스킹 함정 3가지** (`--save-fixture`가 전부 따라야 한다):
1. BeautifulSoup으로 재직렬화하면 **DOM이 변형된다**(본문 274자→16,303자 관측) → 개인정보는
   파싱으로 **찾고** 치환은 **원문 문자열에 정확히**.
2. 렌더링 텍스트만 보면 **속성 안을 놓친다** — 이 게시판은 상세 링크 `title="…"`에 공고 본문을
   통째로 넣는다(연락처 8건이 그렇게 통과했다).
3. **마스킹과 검증이 같은 패턴을 써야 한다.** 다르면 한쪽이 놓친 것을 다른 쪽이 못 잡는다 —
   마스킹 정규식이 "다음 라벨" lookahead를 요구해서 실명 9건을 놓쳤고, 검증 패턴을 조이자
   드러났다. 조직명(`경안노회`)을 사람 이름으로 오판해 본문을 망가뜨린 일도 있다.

### ③④⑤ 설계 결정 (이미 확정 · SPEC §10에 기록)

- **`external_id` 중복은 에러** — 단 "한 실행 안"만 본다. 실행 간 충돌은 **제목·날짜 대조**로 잡는다(추가 요청 0건: 목록 값 ↔ 저장된 `raw_meta.list_title`·`list_date`). 그래서 ③에서 원장 조회가 `{id: (제목, 날짜)}`를 돌려주게 바꾼다.
- **`--dry-run`이 출력할 것**: 행 수 · 공지 제외 수 · **external_id 중복 수** · 게시일 범위 · 원장 신규 수 · 샘플 3건. 31곳 파싱 검증의 도구다.
- **3개월 컷오프 = 목록의 게시일**(구조화 전이라 `posted_at` 없음). 날짜 없는 소스는 `--months 0` 폴백(날짜가 아예 없으면 `--months`는 **실패**시킨다 — 조용히 상한까지 걷지 않는다). **컷오프가 종료를 정하고 페이지 상한(100p)은 폭주 방지용이며 CLI 옵션으로 노출하지 않는다**(운영자 결정 2026-08-04 — 무조건 기간 단위). ⚠️ "새 글 없는 페이지에서 종료"는 폐기됐다(1개월 뒤 3개월 백필이 첫 페이지에서 멈춘다) — 종료 조건은 **페이지 전체가 컷오프 밖**.
- **수집(무료)과 구조화(유료)는 별도 명령** — 파싱이 틀린 채 수백 건을 Gemini에 보내면 되돌릴 수 없다.
