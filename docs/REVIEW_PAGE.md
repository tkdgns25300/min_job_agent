# 크롤러 공고 검수 페이지 — 기능명세

> **누가 읽나** — min_job admin에서 이 페이지를 만드는 사람.
> **누가 썼나** — `min_job_agent`(크롤러) 쪽. 이 페이지가 읽고 쓰는 `review_data`는 크롤러가 소유·마이그레이션하는 테이블이라, **어떤 값이 무슨 뜻이고 무엇을 쓰면 안 되는지**를 이쪽이 안다.
>
> **정본** — 판정 규칙·스키마는 크롤러 리포의 `docs/SPEC.md`가 정본이고, enum 허용값은 `docs/CONTRACT.md` §1이다. 이 문서는 **그것을 화면으로 옮기는 방법**만 담는다. 둘이 어긋나면 SPEC이 이긴다.
>
> ⚠️ **사실과 제안을 갈라 읽어야 한다.**
> - **사실** — 컬럼·enum 값·DB CHECK·판정 규칙·수치. 전부 코드와 실 DB에 대조했고 수치는 실측이다(**1주치를 끝까지 돌린 전량 473건** · 2개월 약 3,700건 환산 · 2026-08-23 재측정). 이건 지켜야 한다.
> - **제안**(🅿️ 표시) — 화면 배치, 배지 이름, 버튼 문구. min_job 쪽이 더 잘 아는 영역이라 바꿔도 된다.

## ✅ 준비 상태 (2026-08-22)

| | |
|---|---|
| `review_data.poster_paths text[]` · `review_note text` | **적용됐다.** 지금 쿼리해도 된다 |
| `postings` 버킷 | **만들어졌다** — 비공개 · 파일당 8MB · MIME 6종 |
| 포스터 업로드 | **동작 확인**(실 공고 1건 · 325KB JPEG가 계약 경로에 올라감) |

✅ **지금 바로 붙여서 개발할 수 있다.** 1주치를 끝까지 돌려 `review_data` **465행**이 들어 있고, 그중 **79행**에 포스터가 달려 있다(검수 큐 76건 중 **61건**). `jobs`에도 **242행**이 공개돼 있다.

⚠️ 다만 **2개월 전량 수집 전이다** — 전량 뒤에는 `review_data`가 약 3,600행, 포스터가 약 620행이 된다. 지금 데이터로 만든 화면이 그대로 커진다.

→ `poster_paths`가 빈 행(465행 중 386행)은 배지 규칙(§4.4) 그대로 처리하면 된다.

## 1. 이 페이지가 하는 일 — 한 문장

크롤러가 **"사람이 봐야 답이 나온다"고 판단한 공고만** 사람이 판정해서, 공개 대기열로 보낸다.

크롤러는 공개까지 자동으로 한다. 이 페이지에 오는 것은 **자동으로 결론이 안 나는 것뿐**이다.

```
게시판 30곳 → 수집 → AI 구조화 → 등급 판정 ─┬─ high    → 자동 승인 → 자동 공개
                                            ├─ 자동 거절 (이단·마감) → 끝
                                            └─ medium/low → 【이 페이지】 → 승인 → 다음 실행이 공개
```

---

## 2. 규모 — 얼마나 오나

**1주치(2026-08-16~23)를 끝까지 돌린 실측**과, 그것을 **2개월**로 환산한 값이다.

| | 1주 실측 | 비율 | 2개월 환산 |
|---|---|---|---|
| 수집 | 473 | 100% | ~3,700 |
| 1차 게이트 탈락 | 8 | 2% | ~60 |
| 초안(`review_data`) | 465 | 98% | ~3,640 |
| 자동 승인(`APPROVED`) | 242 | 51% | ~1,890 |
| **이 페이지에 오는 것**(`PENDING`) | **76** | **16%** | **~590** |
| 자동 거절(`REJECTED`) | 147 | 31% | ~1,150 |
| → 공개된 것(`jobs`) | 242 | 51% | ~1,890 |

⚠️ 1차 게이트 탈락은 **`review_data` 행이 아예 생기지 않는다**(채용 공고가 아니라고 판단한 것).

⚠️ **자동 거절 147건 중 144건이 중복**이다(같은 자리 재게시 · 나머지 3건은 마감). 즉 **위 `PENDING` 76건은 이미 중복을 걷어낸 수**다 — 화면에서 더 줄어들지 않는다.

⚠️ **검수 76건 중 61건(80%)이 "그림 때문"이다.** 포스터 한 장이 본문인 공고는 AI가 그림을 읽었는데, 코드가 "그 글자가 원문에 있나"를 확인할 수 없다(원문이 그림이라 정상이다). 그래서 자동 승인하지 않고 사람에게 넘긴다.

→ **이 페이지의 성능은 "포스터를 얼마나 빨리 볼 수 있나"가 거의 전부를 결정한다.** §7이 그 얘기다.

참고 — 등급(`confidence`)은 `high` 361(78%) · `medium` 80(17%) · `low` 24(5%)이다. ⚠️ **큐는 등급이 아니라 `review_status`로 만든다**(§3).

## 3. 큐 정의 — ⚠️ 가장 중요한 한 줄

```sql
WHERE review_status = 'PENDING'
ORDER BY created_at ASC
```

**필터는 이것뿐이다.** `confidence`로 필터하면 **양쪽으로 어긋난다**:

| 잘못 | 무슨 일이 나나 |
|---|---|
| ❌ `confidence IN ('medium','low')` | **필요 없는 걸 끌어온다** — 이단·마감으로 **이미 자동 거절된** 행이 함께 뜬다(거절은 등급보다 앞선다) |
| ❌ 같은 필터 | **봐야 할 걸 놓친다** — 중복 판정이 `UNCERTAIN`으로 돌린 행은 **등급이 `high`인데 `PENDING`이다**(실측 확인) |

`confidence`는 **"왜 여기 왔나"를 보여주는 값**으로 쓰고, 필터·정렬에 쓰지 않는다.

정렬을 `created_at`으로 하는 이유: 오래 방치된 공고가 먼저 나와야 한다. `posted_at`은 중복 묶음에서 **최신으로 덮이는 파생값**이라 정렬 기준이 될 수 없다.

✅ **스키마가 이 쿼리에 맞춰져 있다** — 인덱스가 이미 있다:

```sql
review_data_queue_idx      (review_status, created_at)   ← 위 쿼리 그대로
review_data_dedup_key_idx  (dedup_key)                   ← §4.3 묶음 화면
```

## 4. 화면 구성

**화면은 셋이다.** 나머지는 이 셋 안의 상태다.

| 화면 | 무엇 | 언제 들어가나 |
|---|---|---|
| **① 큐 목록** | 검수할 것 전부. 무엇을 봐야 하는지 배지로 | 검수를 시작할 때 |
| **② 단건 상세** | 원문과 값을 나란히 놓고 고치고 판정 | 목록에서 한 건을 열 때 |
| **③ 묶음 판정** | 같은 자리인지 사람이 정한다 | `dedup_state='UNCERTAIN'`인 건을 열 때 — ②가 아니라 여기로 간다 |

⚠️ **③은 ②의 변형이 아니라 별개 화면이다.** ②는 "이 값이 맞나"를 묻고 ③은 "이 둘이 같은 자리인가"를 묻는다. 질문이 다르므로 화면도 다르다.

접근은 **운영자 전용**이다(일반 사용자 노출 없음).

### 4.1 ① 큐 목록

| 열 | 컬럼 | 비고 |
|---|---|---|
| 교회명 | `church_name` | 비어 있을 수 있다(그러면 `low`) |
| 지역 | `region` + `city` | |
| 자리 | `position[]` 또는 `role` | `job_kind`가 `MINISTRY`면 `position`, `GENERAL`이면 `role` |
| 부서 | `department` | 69%가 비어 있다 — 비었다고 오류가 아니다 |
| 게시일 | `posted_at` | |
| **왜 걸렸나** | `confidence` + 계산 근거 | 배지로. §4.4 |
| 게시판 | `source_url`에서 유도 | 원문 링크 |
| 들어온 날 | `created_at` | 정렬 기준 |

### 4.2 ② 단건 상세 — 2단 레이아웃

**왼쪽 = 원문 증거 / 오른쪽 = 구조화된 값.** 검수는 "이 값이 저 원문에 맞나"를 보는 일이라, 두 화면을 오가면 못 한다.

```
┌─────────────────────────┬──────────────────────────┐
│ 원문 (source_data)      │ 구조화된 값 (review_data) │
│                         │                          │
│ [포스터 이미지]          │ 교회명  [노원교회    ] ✎  │
│  ↕ 확대·회전            │ 지역    [DAEGU ▾]     ✎  │
│                         │ 직분    [교육전도사 ▾] ✎  │
│ ─ 원문 텍스트 ─         │ …                        │
│ 대구 노원교회 청소년부… │                          │
│                         │                          │
│ 🔗 게시판 원문 열기      │ [승인] [거절] [저장만]    │
└─────────────────────────┴──────────────────────────┘
```

- 왼쪽은 `review_data.source_data_id` → `source_data`를 조인해서 얻는다(§6.6).
- 포스터가 없는 공고(텍스트 본문)는 왼쪽이 텍스트만 된다.

**⚠️ 포스터 뷰어 요구사항** — 여기가 이 화면의 성능을 정한다(검수의 96%)

| 요구 | 왜 |
|---|---|
| **원래 크기로 볼 수 있어야 한다** | 청빙 포스터는 대개 **A4 세로**다. 2단으로 나눈 왼쪽 칸에 맞춰 축소하면 **연락처·사례비 글자를 읽을 수 없다.** 확대(모달·새 탭·좌우 폭 조절) 중 하나는 반드시 있어야 한다 |
| **여러 장 넘기기** | 한 공고에 포스터가 여러 장인 경우가 있다. `poster_paths`의 **배열 순서가 원문 순서**다(§7.1 · 못 받은 것은 빠지고 남은 것의 상대 순서는 그대로) — 순서를 지켜야 말이 된다 |
| **PDF도 같은 자리에** | `.pdf`가 같은 배열에 들어온다. 브라우저 내장 뷰어로 보이므로 이미지와 같이 취급한다 |
| 회전·확대 | 스캔 포스터가 눕거나 해상도가 낮다 🅿️ |

⚠️ **텍스트 공고에서는 원문 텍스트를 검색할 수 있으면 좋다** 🅿️ — 값이 원문 어디서 왔는지 찾는 일이 검수의 대부분이다.

### 4.3 ③ 묶음 판정 — `dedup_state = 'UNCERTAIN'`

크롤러가 **"같은 자리인지 내가 정할 수 없다"** 고 넘긴 건이다. 한 건씩 보여주면 판단이 **불가능하다** — "이게 옆 게시판 것과 같은 자리인가"가 질문이기 때문이다.

**같은 `dedup_key`를 한 화면에 나란히 놓는다** 🅿️:

```
[묶음] 광림교회:SEOUL:ASSOCIATE_PASTOR:-:R1
────────────────────────────────────────────────
① YTUS  08-18  접수 yoon4970@…   ✅ 이미 공개됨
② PCK   08-19  접수 klmchwang93@…   ← 검수 대상

  [ 같은 자리 — ②를 중복 처리 ]
  [ 다른 자리 — ②도 공개 ]
```

⚠️⚠️ **묶음의 일부는 이미 공개돼 있다.** `UNCERTAIN` 묶음에서 크롤러는 **대표는 그대로 내보내고 나머지만 검수로 돌린다**(같은 자리였다면 어차피 하나만 공개돼야 하고, 다른 자리였으면 운영자가 승인하면 된다 — 전원을 검수로 돌리면 같은 자리인 경우에도 두 건을 보게 된다).

→ 묶음 화면은 **"이미 공개된 것 + 미결인 것"이 섞인 상태**를 다뤄야 한다. 구분은 `published_job_id IS NOT NULL`로 한다.

⚠️ **"크롤러가 고른 대표"는 표시할 수 없다.** 대표와 나머지에 **똑같이 `dedup_state='UNCERTAIN'`**이 붙어서, 저장된 값으로는 어느 쪽이 대표였는지 알 수 없다. 대신 `published_job_id`(공개됨)와 `review_status`로 상태를 보여준다.

**왜 `UNCERTAIN`이 되나** — 셋 중 하나다. 화면에 그 이유를 적어 주면 판단이 빨라진다:

| 이유 | 무엇을 보면 되나 |
|---|---|
| 접수 이메일이 다르다 | 담당자가 둘인가, 한 사람이 메일을 바꿔 올렸나 |
| 부서가 여러 값인데 침묵도 섞였다 | 부서를 안 적은 글이 어느 자리에 붙나 |
| 사람이 이미 본 행이 둘 이상 | 정리도 사람이 한다 |

⚠️ **`dedup_key`를 화면에서 편집 가능하게 만들지 않는다.** 크롤러가 매 실행 다시 계산해서 덮는다(판정은 멱등이어야 한다). 사람의 결론은 **`review_status`로 표현**한다 — §5.4.

### 4.4 "왜 걸렸나" 배지 🅿️

등급이 왜 그 값인지를 사람 말로 보여준다. 이게 없으면 검수자가 매번 전체를 다시 훑는다.

**전부 저장된 값으로 계산된다** — 등급 이유를 따로 담는 칸은 두지 않는다.

| 배지 | 판정식 |
|---|---|
| 🖼 **포스터** | `poster_paths`가 비어 있지 않다(§7) |
| 🚫 **그림 못 받음** | `source_data.image_urls`는 있는데 **`poster_paths`가 비었다** — 바이트를 못 받았으면 올릴 것도 없으므로 없다는 사실이 곧 신호다 |
| 🖼⚠️ **일부만 받음** | `cardinality(poster_paths) < cardinality(source_data.image_urls)` — 여러 장 중 일부를 못 받았다(크기 상한·오류). 있는 것만 보여주고 원문 링크를 함께 준다 |
| 📭 **빈 칸** | 승격 6칸 중 빈 칸이 있다(§6.3) — 어느 칸인지도 계산된다 |
| ❓ **채용 공고 아님?** | `is_church_recruitment <> 'YES'` |
| ⛪ **이단 목록 일치(지역 미확인)** | `heresy_flag = true` — 근거는 `heresy_evidence` |
| ✉️ **지원 경로가 우편뿐** | `contact_post`만 차 있다 |
| 🔀 **같은 자리인지 불확실** | `dedup_state = 'UNCERTAIN'` → §4.3 묶음 화면 |
| ⛪❓ **교단 미확정** | `denomination_source IN ('ai_guess','unknown')` — 이대로면 교단이 공개되지 않는다 |

⚠️ 위 **포스터 관련 세 줄**이 검수의 **96%**를 가른다 — 이게 없으면 목록에서 "무엇을 봐야 하나"를 알 수 없다.

⚠️ 배지는 여러 개가 함께 붙을 수 있다(예: 포스터 + 빈 칸).

⚠️ **크롤러의 등급 규칙을 min_job에 베끼지 않는다.** 위 판정식은 **저장된 사실**만 본다. 등급 계산 자체(무엇이 `medium`인가)는 실측으로 계속 바뀌므로 베껴 두면 규칙이 바뀔 때마다 배지가 **조용히** 틀어진다.

⚠️ 배지 이름·이모지는 제안이다. **판정식이 사실이다.**

### 4.5 큐를 실제로 굴리는 데 필요한 것 🅿️

2개월 전량이면 약 590건을 한 건씩 처리해야 한다. 아래가 없으면 화면은 맞는데 **일이 안 끝난다.**

| 기능 | 왜 |
|---|---|
| **키보드 단축키** | 승인·거절·다음. 수백 번 마우스로 옮겨 다니면 검수가 늘어진다. 판단 자체는 포스터를 보는 시간이라 줄일 수 없지만 **이동 시간은 줄인다** |
| **남은 건수 / 오늘 처리한 수** | 끝이 보이지 않으면 손을 못 댄다. 큐 크기는 `count(*) WHERE review_status='PENDING'` |
| **검색·부가 필터** | 교회명·지역·게시판·배지별. ⚠️ **큐 필터(`review_status='PENDING'`)를 대체하는 게 아니라 그 위에 얹는다**(§3) |
| **처리한 것 다시 보기** | `APPROVED`·`REJECTED` 목록. 되돌리기(아래)와 감사에 필요하다 |
| **되돌리기 — 공개 전에는 가능하다** | 아래 별항 |
| **배열 칸 편집** | `position`·`job_kind`와 목록 5칸이 배열이다. 칩(chip) 형태 다중 선택이 맞다 |

**되돌리기 — `published_job_id`가 비어 있으면 아직 안 나갔다**

```sql
UPDATE review_data SET
  review_status = 'PENDING',
  reviewed_by = '<운영자>', reviewed_at = now()
WHERE id = $1 AND published_job_id IS NULL;   -- ⚠️ 이 조건이 안전장치다
```

- 승인해도 **다음 크롤 실행까지는 공개되지 않는다**(§8). 그 사이에는 되돌릴 수 있다.
- 거절도 같은 방식으로 `PENDING`으로 되돌린다 — `reject_reason`을 함께 비운다(§5.5 CHECK). `review_note`는 남겨 둬도 된다(짝이 없는 칸이다).
- ⚠️ **`published_job_id`가 있으면 이미 나갔다** — 그때는 되돌릴 길이 없다(§10). 그래서 위 `WHERE`에 조건을 걸어 **버튼이 조용히 실패하게** 두지 않고 "이미 공개됨"을 보여준다.

**일괄 처리** — 일괄 **승인은 권하지 않는다.** 검수의 96%가 포스터를 봐야 하는 건이라 일괄 승인은 "확인했다"를 거짓으로 만든다. 일괄 **거절**은 같은 사유가 반복될 때(예: 특정 게시판이 채용 공고가 아닌 글을 대량으로 올림) 쓸 만하다.

**동시 검수** — 운영자 1명을 전제로 쓴 문서다. 두 명이 붙으면 같은 행을 각자 판정할 수 있다. 필요해지면 그때 `reviewed_by`·`reviewed_at`으로 "누가 보고 있나"를 표시하는 정도로 충분하다.

### 4.6 화면의 상태와 실패

기능만 있고 이게 없으면 **막힐 때 사람이 무슨 일인지 모른다.**

| 상태 | 무엇을 보여주나 |
|---|---|
| **큐가 비었다** | "검수할 공고가 없습니다." ⚠️ 오류가 아니다 — 자동 승인이 83%라 정상적으로 자주 빈다 |
| 불러오는 중 | 목록·상세 각각 |
| **포스터가 안 뜬다** | `poster_paths`는 있는데 이미지 로드가 실패했다(signed URL 만료 등) → **원문 링크를 크게** 띄운다. 배지 🚫와는 다른 상황이다(그건 애초에 경로가 없는 것) |
| **원문 텍스트가 빈 문자열** | ⚠️ **정상이다** — 본문이 이미지 한 장인 게시판이 있다. "원문이 그림입니다"로 안내한다 |
| 저장 실패 | 아래 표로 사람 말로 바꿔 준다 |
| **되돌리기가 0행 갱신** | "이미 공개되어 되돌릴 수 없습니다"(§4.5의 `WHERE ... published_job_id IS NULL`) |

**⚠️ DB CHECK 위반(`23514`)을 사람 말로** — Postgres 오류 메시지에 제약 이름이 들어오므로 이름으로 갈라 준다:

| 제약 이름 | 보여줄 말 |
|---|---|
| `review_data_rejection_needs_reason` | 거절에는 사유가 있어야 하고, 승인하려면 사유를 비워야 합니다 |
| `review_data_duplicate_pairs_with_state` | 중복 거절을 풀 때는 중복 라벨(`dedup_state`)도 함께 비워야 합니다 |
| `review_data_kind_matches_seat` | 종류(사역/일반)와 직분·직무명이 맞지 않습니다 — 사역이면 직분, 일반이면 직무명이 있어야 합니다 |
| `review_data_source_requires_denomination` | 교단을 지우려면 교단 근거도 "미상"으로 내려야 합니다 |
| `review_data_pay_range` / `pay_min_check` / `pay_max_check` | 사례비 범위가 뒤집혔거나 음수입니다 |
| `review_data_dedup_state_needs_key` | 중복 라벨은 키 없이 설 수 없습니다 |

→ **가능하면 저장 전에 화면에서 막는다.** DB는 마지막 방어선이고, 여기까지 오면 사람이 이미 입력을 끝낸 뒤다.

### 4.7 검수 한 건의 흐름

96%가 포스터 건이므로 실제 순서는 이렇게 된다 🅿️:

```
① 배지를 본다            → 무엇을 확인해야 하나
② 포스터를 원래 크기로 본다 → (포스터 건이면 값 전체가 미확인이다 · §6.1)
③ 승격 6칸을 맞춘다       → 비면 승인 버튼이 안 눌린다 (§6.3)
④ 나머지 칸을 훑는다       → ⚠️ 표시된 칸(조립됨)과 교단만 보면 된다 (§6.1)
⑤ 판정                   → 승인 / 거절(사유) / 저장만
```

**승인 버튼을 막아야 하는 조건**

| 조건 | 왜 |
|---|---|
| 승격 6칸 중 빈 칸이 있다 | min_job이 공개를 거부한다(§6.3) |
| `is_church_recruitment <> 'YES'` 인데 그대로 승인 | 채용 공고가 아닌 것을 공개하게 된다 — 최소한 확인을 한 번 받는다 🅿️ |
| `heresy_flag = true` 인데 그대로 승인 | 이단 목록에 걸린 건이다 — 지역을 확인했는지 확인을 받는다 🅿️ |

⚠️ **교단 미확정(`ai_guess`)은 막지 않는다.** 교단이 비어도 공개는 된다 — 교단 칸만 비게 나간다(§6.4). 경고로 보여주고 승인은 허용한다.

## 5. 액션 — DB 쓰기 계약

⚠️ **이 절이 이 문서의 핵심이다.** 여기서 어긋나면 조용히 틀리지 않고 대부분 DB가 막지만(§5.5), 막지 못하는 함정 하나가 §5.4에 있다.

### 5.1 승인

**보통(`PENDING` → `APPROVED`)**

```sql
UPDATE review_data SET
  review_status = 'APPROVED',
  reviewed_by   = '<운영자 식별자>',
  reviewed_at   = now()
WHERE id = $1;
```

**거절된 행을 되살려 승인할 때** — `reject_reason`을 비우고, 그게 `'DUPLICATE'`였다면 `dedup_state`도 함께 풀어야 한다(§5.5):

```sql
UPDATE review_data SET
  review_status = 'APPROVED',
  reject_reason = NULL,
  dedup_state   = NULL,          -- reject_reason 이 'DUPLICATE' 였을 때만
  reviewed_by   = '<운영자 식별자>',
  reviewed_at   = now()
WHERE id = $1;
```

⚠️ **`dedup_state`를 비운 행은 중복 판정을 한 번 더 거쳐야 공개된다.** 크롤러는 라벨 없는 행을 내보내지 않는다(그러면 같은 자리가 여러 건 뜬다). 다음 실행의 중복 판정이 라벨을 다시 붙인 뒤 공개된다 — **크롤러 쪽에서 지켜야 하는 순서**이고 min_job이 할 일은 없다.

- **`reviewed_by`는 반드시 채운다.** 이 칸이 "사람이 손댔다"는 정본 표시다. 자동 승인은 이 칸을 **비워 둔다** — 크롤러는 이 칸에 값을 **만들지 않는다**(읽은 값을 그대로 되쓰기만 한다).
- **값을 고쳤다면 그 칸들도 같은 UPDATE에** 넣는다(§5.3 · §5.5의 CHECK를 함께 볼 것).
- **공개는 즉시가 아니다** — §8.

### 5.2 거절

```sql
UPDATE review_data SET
  review_status   = 'REJECTED',
  reject_reason   = 'OPERATOR',    -- ⚠️ 항상 이 값. 다른 값을 쓰지 않는다 (§5.4)
  review_note     = '값이 틀렸는데 포스터로도 확인이 안 된다', -- 신설 컬럼 · 자유 텍스트
  reviewed_by     = '<운영자 식별자>',
  reviewed_at     = now()
WHERE id = $1;
```

⚠️ **거절하려는 행이 이미 `dedup_state='DUPLICATE'`라면** `dedup_state`도 `NULL`로 함께 비운다 — `reject_reason`이 `'OPERATOR'`로 바뀌면서 짝이 깨지기 때문이다(§5.5). 크롤러가 이미 중복으로 거절해 둔 행을 사람이 "내 결론으로" 확정하는 경우가 그렇다.

⚠️ **거절 사유를 목록(enum)으로 만들지 않았습니다**(2026-08-22 결정). 어떤 이유가 실제로 반복되는지 **실측이 0건**이라, 목록을 먼저 만들면 검수자가 없는 항목을 만났을 때 **가장 가까운 값을 억지로 고릅니다** — 그 데이터로 규칙을 고치면 틀린 근거로 고치게 됩니다. 자유 텍스트가 쌓인 뒤에 그것을 보고 목록을 만듭니다.

→ 그래서 지금은 **`review_note` 자유 텍스트 하나**입니다. 될 수 있으면 **왜 거절했는지 한 줄**을 남겨 주세요. 여기 쌓이는 말이 다음 규칙 개선의 근거가 됩니다:

| 반복되는 말이 뜻하는 것 | |
|---|---|
| "중복이다" | 중복 규칙이 새고 있다 |
| "마감됐다" | 마감 판정이 놓치고 있다 |
| "이단이다" | 이단 목록에 추가할 이름이다 |
| "값이 틀렸다" | 프롬프트를 고칠 근거다 |
| "채용 공고가 아니다" | 1차 게이트가 새는 곳이다 |

⚠️ `review_note`는 **거절 전용이 아닙니다** — 승인할 때 남기는 메모도 됩니다(그래서 `review_status`와 짝을 맺는 CHECK가 없습니다).

### 5.3 저장만 (승인 없이 값 수정)

```sql
UPDATE review_data SET
  <고친 칸들> = …,
  reviewed_by = '<운영자 식별자>',   -- ⚠️ 저장 시에도 채운다
  reviewed_at = now()
WHERE id = $1;
-- review_status 는 'PENDING' 그대로
```

⚠️ **저장 시에도 `reviewed_by`를 채워 달라.** 이게 없으면 "사람이 고쳤지만 아직 승인 전"인 행을 크롤러가 알아볼 수 없고, **다음 재구조화가 사람의 교정을 AI 초안으로 되돌린다.** 지금 우리가 못 막는 유일한 구멍이 정확히 이것이다.

### 5.4 ⚠️⚠️ 묶음 판정 — 중복을 `reject_reason='DUPLICATE'`로 쓰면 안 된다

**실측으로 확인했다.** 검수자가 ②를 중복이라고 판단해 `reject_reason='DUPLICATE'`로 거절하면:

```
① reject_reason='DUPLICATE'  → 다음 실행이 UNCERTAIN/PENDING 으로 되돌린다  ⚠️ 거절이 풀린다
② reject_reason='OPERATOR'   → 판정 대상에서 아예 빠진다                    ✅ 거절이 유지된다
```

**왜** — 크롤러는 `DUPLICATE`를 **자기가 내린 판정**으로 취급한다. 중복 규칙은 실측으로 계속 바뀌기 때문에, 규칙을 고쳐 다시 돌리면 **잘못 거절한 행이 되살아나야** 한다. 그래서 매 실행 처음부터 다시 본다. 사람이 그 값을 쓰면 사람의 결론이 크롤러의 임시 판정으로 오인된다.

`OPERATOR`·`HERESY`·`CLOSED`는 **결론이 난 것**으로 보고 판정에서 제외한다.

→ **묶음 화면의 두 버튼은 이렇게 쓴다:**

| 버튼 | 무엇을 쓰나 |
|---|---|
| **같은 자리 — ②를 중복 처리** | **②만** 쓴다: `review_status='REJECTED'` · `reject_reason='OPERATOR'` · `review_note`(예: `①과 같은 자리`) · `reviewed_by` · `reviewed_at` |
| **다른 자리 — ②도 공개** | **②만** 쓴다: `review_status='APPROVED'` · `reviewed_by` · `reviewed_at` |

⚠️ **이미 공개된 ①에는 쓰지 않는다.** 그 행은 크롤러가 이미 승인·공개했고(§4.3), 손대면 `published_job_id`가 걸린 행의 판정을 바꾸는 일이 된다. ①이 아직 `PENDING`이면(대표가 `medium`이었던 경우) 그때는 ①도 §5.1로 승인한다.

⚠️ `dedup_state`는 `UNCERTAIN`으로 남겨 둔다 — 그 자리는 **끌어올림(재게시 시 날짜 갱신)을 받지 못한다**(끌어올림은 `MASTER`만 받는다). 알고 넘어가는 제약이다.

### 5.5 DB가 막아 주는 것 — 검수 화면이 밟을 수 있는 CHECK 전부

⚠️ 어기면 **조용히 틀리지 않고 `23514`로 실패한다.** 그래서 화면 쪽에서 미리 막아 주는 편이 낫다.

| 제약 | 뜻 | 검수 화면에서 밟는 길 |
|---|---|---|
| `(review_status='REJECTED') = (reject_reason IS NOT NULL)` | 거절과 사유는 한 몸 | 거절 행을 **승인**할 때 `reject_reason`을 안 비움 / 거절하면서 사유를 안 넣음 |
| `(reject_reason='DUPLICATE') = (dedup_state='DUPLICATE')` | 중복 거절과 중복 라벨은 한 몸 | 중복 거절을 **풀 때** `dedup_state`를 안 풂 |
| `dedup_state IS NULL OR dedup_key IS NOT NULL` | 라벨은 키 없이 못 선다 | `dedup_key`만 지움 |
| ⚠️ **`job_kind` ↔ 자리 짝** | `MINISTRY`면 `position`이 있어야 하고 `GENERAL`이면 `role`이 있어야 한다. **역도 성립한다** | **`position`을 지우거나 채울 때** `job_kind`를 같이 안 고침 — 가장 밟기 쉬운 길이다 |
| ⚠️ **`denomination_source` ↔ 교단** | `'unknown'`이 아니면 `denomination`이 있어야 하고 `'UNKNOWN'`이 아니어야 한다 | **교단을 지울 때** `denomination_source`를 `'unknown'`으로 안 내림 |
| ⚠️ `pay_min <= pay_max` · 둘 다 `>= 0` | | 사례비를 고칠 때 |
| `heresy_flag` → `heresy_evidence` 필수 | 근거 없는 플래그를 못 세운다 | (편집 대상이 아니다) |
| `is_church_recruitment='UNCERTAIN'` → `confidence='low'` | | (편집 대상이 아니다) |

**정확한 정의**(실 DB에서 뜬 것):

```sql
review_data_kind_matches_seat  CHECK (CASE
    WHEN cardinality(job_kind) = 0 THEN cardinality(position) = 0 AND role IS NULL
    ELSE ('MINISTRY' = ANY(job_kind)) = (cardinality(position) > 0)
     AND ('GENERAL'  = ANY(job_kind)) = (role IS NOT NULL)
  END)

review_data_source_requires_denomination  CHECK (
    denomination_source = 'unknown'
    OR (denomination IS NOT NULL AND denomination <> 'UNKNOWN'))
```

→ **UPDATE는 한 번에 원자적으로** 보낸다. 나눠 보내면 중간 상태가 CHECK에 걸린다.

### 5.6 ⚠️ 하지 말아야 할 것

| 하지 말 것 | 왜 |
|---|---|
| `source_data`에 쓰기 | **write-once 원문 증거**다. 판정을 되짚는 유일한 근거이고 재취득이 안 된다(게시판이 글을 지운다). 법적 삭제 요청만 예외 |
| `dedup_key` 편집 | 크롤러가 매 실행 다시 계산해 덮는다. 사람의 결론은 `review_status`로 표현한다 |
| `dedup_state` 편집 | 같은 이유. ⚠️ **예외 하나** — 중복 거절을 풀 때는 `NULL`로 함께 비워야 한다(§5.1 · DB CHECK가 강제한다) |
| `confidence` 편집 | 크롤러의 **측정값**이다. ⚠️ 게다가 사람이 손댄 행은 재구조화가 건드리지 않으므로 **고친 값이 영구히 남아** "왜 검수에 왔나"의 근거가 영영 틀어진다 |
| `published_job_id` 편집 | 크롤러가 공개할 때 자기가 채운다. 지우면 같은 공고를 두 번 공개한다 |
| `jobs`에 직접 INSERT | 크롤러가 한다(§8). 직접 넣으면 크롤러가 그 행을 모르고 또 넣는다 |
| 승인 즉시 공개를 기대 | 다음 크롤 실행이 공개한다(§8) |

## 6. 필드 명세

### 6.1 ⚠️ 값마다 "얼마나 믿을 수 있나"가 다르다 — 이걸 UI에 표시해야 한다

크롤러는 AI 답을 원문과 대조해서, **못 찾은 값은 그 칸만 비운다**("빈 칸 > 틀린 값"). 하지만 **모든 칸을 대조하지는 못한다.** 검수자가 어디를 봐야 하는지는 이 차이에서 나온다.

| 등급 | 뜻 | 검수자가 할 일 |
|---|---|---|
| ⭐ **대조됨** | 원문에 그 글자가 있는지 코드가 확인했다. 없으면 비웠다 | 값이 있으면 대개 맞다. **빠르게 지나가도 된다** |
| ⚠️ **조립됨** | 프롬프트가 **여러 조각을 이어 붙이라고 시킨** 칸이다. 원문과 글자가 안 맞는 게 정상이라 세기만 한다 | **눈으로 봐야 한다** |
| 🤖 **AI가 쓴 글** | 원문에 없는 문장이다(요약) | **눈으로 봐야 한다** |
| 🔧 **코드가 만든 값** | AI가 아니라 코드가 계산했다 | 실행마다 흔들리지 않는다. 신뢰도 높음 |
| 🖼 **포스터 공고는 전부 미대조** | 원문이 그림이라 "본문에 없다"가 정상이다. 어느 칸도 비우지 않았다 | **값 전체를 포스터와 대조** |

**⚠️ 화면에 어떻게 표시하나 — 공고 종류에 따라 다르다** 🅿️

| 공고 | 표시 방법 | 왜 |
|---|---|---|
| **포스터 건**(검수의 96%) | **레코드 단위 배너 하나** — "원문이 그림입니다. 값 전체를 포스터와 대조하세요." | ⚠️ **필드별 ⭐ 표시가 오히려 거짓말이 된다.** 그림을 보낸 공고에서는 코드가 **어느 칸도 대조하지 않았다** — ⭐를 칸마다 붙이면 "이건 확인됐다"로 읽히는데 사실이 아니다 |
| **텍스트 건** | **필드별 표시**(⭐/⚠️/🤖) | 여기서는 등급이 칸마다 실제로 다르다. ⚠️와 🤖만 보면 되므로 검수가 크게 빨라진다 |

⚠️ 실제로 **⚠️(조립됨)·🤖(AI가 쓴 글)에만 표시를 붙이는 편이 낫다** — ⭐가 대부분이라 다 칠하면 눈에 안 들어온다. "표시된 칸만 보면 된다"가 되어야 쓸모가 있다.

⚠️ **`region`은 ⭐인데 예외가 있다**(§6.2 각주): 코드는 *근거가 원문에 있나*만 보고 *그 근거가 그 값을 뒷받침하나*는 못 본다. **지역은 항상 눈으로 확인**하는 편이 낫다.

**값이 수정됐다는 표시도 필요하다** — 검수자가 고친 칸을 원본과 구별해 보여주면(예: `[수정됨]` 칩) 판정 직전에 무엇을 바꿨는지 한눈에 확인된다 🅿️.

### 6.3 승격 6칸 — 비면 공개가 거부된다

`church_name` · `title` · `job_kind` · (`position` 또는 `role`) · `description` · (연락처 4칸 중 하나)

하나라도 비면 min_job이 공개를 거부한다. → **승인 버튼을 비활성화**하고 어느 칸이 비었는지 표시한다.

### 6.4 ⚠️ 교단은 값만 고쳐서는 공개되지 않는다

크롤러는 **확정된 교단만** 공개한다. `denomination_source`가 판정 기준이다:

| `denomination_source` | 공개되나 | 뜻 |
|---|---|---|
| `stated` | ✅ | 공고가 교단을 명시했다 |
| `registry` | ✅ | 교단 명부에서 확인했다 |
| `operator` | ✅ | **사람이 확정했다** |
| `ai_guess` | ❌ | AI 추정 — 값이 있어도 안 나간다 |
| `unknown` | ❌ | 모른다 |

→ **검수자가 교단을 고치면 `denomination_source='operator'`도 함께 써야 한다.** 안 쓰면 화면에는 교단이 보이는데 공개된 공고에는 비어 있다.

→ 반대로 **교단을 지우려면** `denomination_source='unknown'`으로 함께 내려야 한다(§5.5 CHECK).

⚠️ `denomination`은 `UNKNOWN`이라는 값도 가질 수 있는데, 그건 공개되지 않는다. 화면에서는 "미상"으로 보여주고 선택지에서 빼는 편이 낫다 🅿️.

### 6.5 ✅ 검수자가 고친 값은 판정에 덮이지 않는다

크롤러의 중복 판정은 **바뀌는 칸만 보낸다**(2026-08-22):

| 무엇을 쓸 때 | 보내는 칸 |
|---|---|
| 라벨만 | `dedup_key` · `dedup_state` |
| 판정까지 | 위 둘 + `review_status` · `reject_reason` · `posted_at` |

그래서 검수자가 그 사이에 `church_name`·`region` 같은 값을 고쳐도 **크롤러가 덮을 수 없다** — 그 칸을 애초에 보내지 않습니다.

⚠️ 반대로 **위 목록 안의 칸**(특히 `dedup_key`·`dedup_state`)은 매 실행 다시 계산돼 덮이므로 화면에서 편집 가능하게 만들지 않는다(§5.6).

### 6.6 원문 쪽 (`source_data` 조인)

`review_data.source_data_id` → `source_data.id` — ⚠️ **1:1이다**(`source_data_id`에 UNIQUE가 걸려 있다). 원문 하나에 초안은 하나뿐이고, 재구조화는 그 행을 갈아끼운다.

| 컬럼 | 쓰임 |
|---|---|
| `raw_text` | 원문 텍스트. ⚠️ **빈 문자열이 정상인 게시판이 있다**(본문이 이미지 한 장) |

| `attachments` (jsonb) | 첨부(PDF·HWP 등). 모양은 `[{"name": "청빙공고.pdf", "url": "…"}]` — **이름을 함께 저장한다**(이 게시판들의 다운로드 URL에 파일명이 없다) |

## 7. 포스터 표시 — Supabase Storage

검수의 96%가 포스터 케이스이므로, 이게 안 뜨면 페이지가 무용하다.

⚠️ **원본 게시판 URL을 그대로 `<img src>`에 넣으면 최소 5~7곳이 안 뜬다:**

| 문제 | 게시판 | 브라우저가 하는 일 |
|---|---|---|
| `http_only` 2곳 | CALVIN · WGST | https 페이지에서 **mixed content 차단** |
| `insecure_tls` 3곳 | DAESHIN · PUTS · KTS | **인증서 오류로 거부** |
| `needs_session` 2곳 | CALVIN · CSU | 쿠키 없이 403/리다이렉트 |
| referer 차단 | 알 수 없음 | 한국 CMS에 흔하다 — 사전에 열거할 수 없다 |

**→ 크롤러가 Supabase Storage에 복사한다.** 구조화 단계에서 이미 그림 바이트를 받아 AI에 보내고 있으므로(인쇄용 CMYK를 화면용으로 변환하는 처리까지 한다), 그 바이트를 올리는 일이 추가된다.

⚠️ **채용 공고로 판정된 것만 올린다** — 1차 게이트에서 탈락한 글(전량의 4% 추정)은 `review_data` 행이 생기지 않으므로 그 포스터도 보관하지 않는다.

### 7.1 계약 (확정)

| | |
|---|---|
| 담당 | **크롤러가 올린다**(구조화 단계 · §11) |
| 버킷 | `postings` — **비공개 버킷**(공개 URL 없음) |
| 경로 | `{source_key}/{source_data_id}/{n}.{ext}` — 예: `YTUS/d38ae0db-…/0.jpg` |
| 순서 | `n`은 **받은 것만 0부터**다. ⚠️ 원문의 절대 인덱스가 아니다 — 못 받은 그림은 목록에 없다. **상대 순서는 원문 그대로**라 여러 장인 공고도 순서가 맞는다 |
| 읽는 방법 | **`review_data.poster_paths text[]`** — 그 행의 그림 경로들. 조인 없이 목록에서도 쓸 수 있다 |
| 화면에 띄우기 | 비공개 버킷이므로 **서버에서 signed URL을 만들어** 내려준다(`createSignedUrl`). 경로를 그대로 `<img src>`에 넣으면 안 된다 |
| PDF | 같은 배열에 들어간다(`.pdf`). 브라우저 내장 뷰어로 보이므로 이미지와 같이 취급해도 된다 |
| HWP·DOC | **올리지 않는다** — 브라우저가 못 열어서 올려도 못 본다. `source_data.attachments`의 원본 링크로 준다 |

**`poster_paths`를 `review_data`에 두는 이유**

| 대안 | 왜 안 되나 |
|---|---|
| `source_data`에 칸 추가 | 그 테이블은 **write-once 원문 증거**다. 업로드는 구조화 시점이라 나중에 쓰게 되는데, 갱신 허용 칸이 3개뿐이고 4번째를 더하면 그 보호가 느슨해진다 |
| 칸 없이 경로를 계산 | 파일 **개수와 확장자를 모르면** URL을 만들 수 없다. 매 행마다 Storage 목록을 조회하면 목록 화면이 느려진다 |

⚠️ 재구조화하면 `poster_paths`도 다시 채워진다(그 행 자체가 갈아끼워진다). Storage 파일은 `source_data_id`로 묶여 있어 그대로 재사용된다.

✅ **덤** — 게시판이 글을 지워도 증거가 남는다. 지금은 원문 URL이 죽으면 판정을 되짚을 근거가 사라진다.

✅ **Storage에 있나 없나가 그대로 배지가 된다**(§4.4):

| `source_data.image_urls` | Storage | 뜻 | 검수자가 할 일 |
|---|---|---|---|
| 있음 | 있음 | 포스터 공고 | 포스터를 보고 값을 확인한다 |
| 있음 | **없음** | **그림을 못 받았다** | **원문 링크를 열어야 한다** |
| 없음 | — | 텍스트 본문 | 원문 텍스트로 확인한다 |

바이트를 못 받았으면 올릴 것도 없으니, **없다는 사실 자체가 신호다.** 그래서 이걸 위한 별도 칸을 두지 않는다.

⚠️ **첨부는 종류를 가려야 한다.** PDF는 브라우저에서 보이지만 HWP·DOC는 안 보인다 — 그건 다운로드 링크로만 준다(`attachments[].name`의 확장자로 가른다).

원문 링크(`source_url`)는 **함께** 제공한다 — 포스터로 안 되는 판단이 있고, 검수자가 원문 맥락을 볼 때가 있다.

## 8. ⚠️ 승인해도 즉시 공개되지 않는다

```
검수자가 승인 → review_data.review_status='APPROVED'
                        ↓
             【다음 크롤 실행의 publish 단계】
                        ↓
              jobs 에 INSERT → 목록에 뜬다
```

**크롤러가 공개한다.** 이 페이지는 `jobs`를 건드리지 않는다.

이유: 공개는 중복 판정이 끝난 뒤에만 안전하다. 승인 즉시 넣으면 같은 자리가 여러 건 뜬다.

→ **UI에 "다음 수집 실행 시 공개됩니다"를 표시**해야 한다. 안 하면 검수자가 승인하고 목록을 확인하러 갔다가 "안 됐다"고 판단해 다시 누른다.

⚠️ 지금은 `publish`가 `structure` 뒤에 자동으로 이어지지 않는다(운영자가 명령을 돌린다). 자동 스케줄을 붙일 때 이 순서가 한 명령으로 묶인다.

### 공개된 뒤에 일어나는 일

| | |
|---|---|
| **끌어올림** | 같은 자리가 다른 게시판에 다시 올라오면 `jobs.posted_at`을 최신으로 민다(`MASTER`만) |
| **교회가 claim** | 교회가 min_job에서 그 공고를 자기 것으로 가져가면(`church_id` 채워짐) 크롤러는 **손을 뗀다** |
| ⚠️ **회수 경로 없음** | 공개한 뒤 "잘못 승인했다"를 되돌리는 길이 지금 없다. §10 |

## 9. 권한

- **RLS는 열려 있고 접근은 `service_role`로 한다**(운영자 결정). 크롤러도 전용 롤 없이 service key를 쓴다.
- 그래서 **경계는 코드가 지킨다**: 크롤러는 `jobs`에 **읽기 + INSERT + `posted_at` 한 칸**만 쓰고 `churches`에는 쓰지 않는다. 이 페이지가 지켜야 할 경계는 §5.6이다.
- Storage 버킷은 비공개다 — 화면에 띄울 때 signed URL을 만든다(§7.1).

### ⚠️ 크롤러가 복제해 둔 규칙 하나 — 바뀌면 알려 주세요

크롤러는 중복을 막으려고 `jobs`를 읽어 **"이 자리가 이미 목록에 떠 있나"** 를 봅니다(앵커). 그 판정은 min_job의 "목록에 보이는가"와 **글자 그대로 같아야** 합니다. 지금 크롤러가 들고 있는 사본은 이것입니다(min_job `DATA.md` §6-1에서 옮긴 것):

```
목록에 보인다 =  status = 'OPEN'
             AND (deadline IS NOT NULL  ?  deadline >= 오늘
                                        :  posted_at + 90일 >= 오늘)
```

**어긋나면**: min_job은 보여주는데 크롤러는 "안 보인다"고 판단 → 그 자리의 재게시를 **새 공고로 공개** → **목록에 같은 자리 2건**이 뜹니다.

| 알려 주셔야 하는 변경 | 왜 |
|---|---|
| **`status`에 "보이는" 값이 추가될 때** | 크롤러는 `='OPEN'`만 봅니다. 값이 **줄어드는 건 안전**합니다(`PENDING` 제거처럼) — **늘어나는 방향**이 위험합니다 |
| **90일이 바뀔 때** | 상시모집(마감일 없음) 공고의 노출 기간입니다 |

⚠️ **`jobs_visible` 뷰는 두지 않기로 했습니다**(2026-08-22 운영자 결정). 두 리포 모두 **DB는 저장 전용**이고 뷰도 판정 규칙을 DB에 넣는 것이라 예외를 두지 않습니다. 그래서 이 사본은 **통보로 지킵니다.**
